# チーム運用憲章（TEAM.md）

初版: 2026-11-23 / 改訂: 2026-11-24（X 記事および「T3 Code: Building Multi-Agent Workflows」の運用規則と 3.1 の追補を本環境構成に合わせて統合）。

置き場は本スキル（`t3-agent-ops`）配下で、`SKILL.md` と対で使う。プロジェクト側で憲章（charter）が必要な場合は本書をコピーし、そのプロジェクトの `AGENTS.md` 等から参照させる。

モデル名は表示名で書く。スレッド作成時にモデル一覧の slug が表示名と異なる場合は、一覧で対応するモデルを選ぶ。

---

## 1. 目的と適用範囲

本憲章は、T3 Code（AI エージェントのスレッドを作成・実行・管理するツール、本環境では `v0.1.11`）を経由して行うすべての作業委任に適用する。

- 作業の発起は人間（ユーザー）が行い、統括役の Muse（Nao）がユーザー指示を受けて T3 Code 上にスレッドを作成する。
- チームはモデル名ではなく**役割の契約**（触ってよい範囲、返すべき成果物、誰が検証するか）で定義し、モデル割り当てはその契約に対して行う。
- 子エージェント（委任先スレッドで動作するエージェント）は親スレッドの文脈を参照できないため、各スレッドの実行に必要な情報はすべて brief（委任先へ渡す作業指示書）単体で完結させる。
- 新規作業は各マシンの `~/agentic-project` 配下に配置し、依存関係は `pixi` または `uv`（パッケージおよび環境管理ツール）で管理する。

## 2. 構成と禁止事項

### 2.1 マシン構成

T3 Code `v0.1.11` は 5 台に常駐し、待受は各台の tailnet IP の `3773` 番ポートのみとする（T3 Connect 不使用、2.4）。各マシンの詳細構成は `SKILL.md` を参照し、実作業の主な実行先は `gpu-01` とする。

### 2.2 provider とモデル構成

provider（T3 Code からモデル実行基盤へ接続する種別）ごとに、使用するモデルは以下の通りとする。

- **antigravity**（公式 `antigravity-acp`〔Agent Client Protocol クライアント〕+ `oauth-personal`〔個人アカウントの OAuth 認証〕、全台で instance 名は `antigravity`）: `gemini-4-neon`（既定）、`gemini-4-argon`、`gemini-4-hydrogen`（役割表の割り当てなし）、`gemini-pro-orchestrator-neon`、`gemini-pro-orchestrator-g1-pro`、`claude-opus-5-5`、`claude-sonnet-5-5`
- **claudeAgent**（裏側は各マシンの Claude Code + M4 Mac mini の CLIProxyAPI〔CPA〕）: `gpt-6-luna`、`gpt-6.1-terra`（役割表の割り当てなし）、`preview/DeepSeek-V4.1-Flash-1017`
  - DeepSeek はさくらインターネット（さくらの AI Engine）のモデルで、CPA 経由で使う。基盤モデルの無償プランは Chat Completions 月 3,000 リクエストまで無料で、この枠内で使う（超過時はレート制限のみ、自動課金・自動移行なし）。
- **acpRegistry_devin**: `SWE-2`、`claude fable 5.2`、`claude opus 5.5`、`gpt-6.2 astra`、`claude sonnet 5.5`、`gpt-6.2 sol`
- **grok**（Grok Build CLI）: `grok-4.7`

### 2.3 Opus / Sonnet の使用経路

- Opus 5.5 と Sonnet 5.5 は、まず `antigravity` 側から使用する。
- Google クォータがなくなったら、`acpRegistry_devin` 側の `claude opus 5.5` / `claude sonnet 5.5` に切り替える。切り替えた場合はその旨を報告する。

### 2.4 運用上の禁止事項

- `antigravity` は公式 `antigravity-acp` + `oauth-personal` のみを使用する。トークン抽出、プロキシ経由の迂回、アカウントローテーションは行わない。
- 無人・自動のバックグラウンド処理として Antigravity スレッドを実行しない。
- T3 Connect を開けて外部の常駐 Bot（Grok Bot ディスパッチャ等）からスレッドを起票させない。起票と振り分けは Muse がユーザーの指示を受けて行う。
- 認証情報（トークン、パスワード、API キー等）をファイルやチャットに記載しない。

### 3.1 計画・指揮の中での Neon / Opus の使い分け（2026-11-24 追補）

- **設計・アーキテクチャは Neon 先行**: 新規方式、大胆な構造変更、行き詰まったときの大きな一手。
- **改善・最適化は Opus 先行**: 既存案の組み合わせ、パラメータ調整、リファクタや最適化の段取り（実装自体は実装役が担う）。
- 先行順の目安であり、Argon、Fable、Orchestrator の従来の割り当ては変えない。
- 根拠: Harris の autoresearch 実験（リポジトリ `harris-nyc/neon-autoresearch`）で、Neon の改善幅が Opus の 1.76 倍で、Neon は大きな構造変更、Opus は届かなかった案同士の組み合わせが得意だった。数値の詳細は同リポジトリと MEMORY.md に残し、本書には載せない。
- 限界: 1 回・1 タスクの結果で、推論設定も Neon high / Opus medium とそろっていない。一般的な順位として扱わず、新しい同種の実測が出たら見直す。「実装は軽量モデル」はこの実験に根拠がないため採用しない。
- 停滞判定: Neon は 1 件あたり中央値約 8 分（Opus は約 1.5 分）が通常運転。9.1 を Neon に適用するときは確認間隔を長めに取る。

## 4. ルーティング規則と並列実行・統合

### 4.1 作業種別ごとのルーティング

| 作業の種類 | 最初に渡す先 | 次の手 |
| :--- | :--- | :--- |
| 新規実装・機能改修 | 計画・指揮（3 の担当モデル） | 計画を確認 → 実装（3 の担当モデル。並列時は 4.3 に従い分離・join） → 実装レビュー（第 6 節に従い別ファミリーで実施） → Muse が成果物・テスト結果を検証 |
| 新規アーキテクチャ・設計の探索 | 計画・指揮のうち Neon 先行（3.1） | 設計案を確認 → 必要に応じ Argon / Fable / Orchestrator で補完 → 実装へ |
| 既存実装の改善・最適化・リファクタの段取り | 計画・指揮のうち Opus 先行（3.1、2.3 の経路に従う） | 改善案と組み合わせ方針を確認 → 実装（3 の担当モデル） → 実装レビュー（第 6 節） |
| 文書の起草・構成変更 | 文書起草（Gemini 系） | Muse が原文・根拠・数値と照合 → 必要に応じ別ファミリーのモデルでレビュー |
| 調査・情報収集 | 調査（`grok-4.7`） | 調査結果を成果物ファイルへ記録 → 必要に応じ計画・指揮または文書起草へ引き継ぎ |
| 運用チェック・軽作業 | 軽作業・運用チェック（3 の担当モデル） | Muse が実行ログと成果物を確認し完了判定 |
| レビュー単体 | 実装レビュー（Sol / Astra。実装が同ファミリーの場合は別ファミリー）。文書レビューは起草と別ファミリー | 指摘事項と `checks` 結果を出力 → severity 1〜2 の修正が必要な場合は実装または文書起草へ戻す（第 6 節） |

### 4.2 受け渡しとレビューの機械的な上限

委任実行の停止条件は、「完了条件やレビューによる意味的な判定」に加えて、モデルが解釈で延長できない**機械的な上限**の二本立てとする。

- **エージェント間の受け渡し上限**: 人間を挟まず **最大 4 回** までとする。
- **レビューループの上限**: **最大 3 ラウンド** までとする。
- **上限到達時の扱い（Silent caps の禁止）**: 受け渡し 4 回またはレビュー 3 ラウンドに達して終了した場合、**「完了」「成功」として報告してはならない**。必ず完了とは別の結果区分である **「上限到達」** として記録・報告し、判断を人間（ユーザー）へ上げる。

### 4.3 直列化と並列実行（slice 分離・join）

- **同一ファイルの直列化（基本原則）**: 複数のスレッドが同一ファイルを変更対象とする場合、2 つ目のスレッドは先行スレッドの完了まで待機させ、直列化（1 件ずつ順番に実行）する。
- **並列実行の適用条件**: 並列実装を行うのは、作業が**ファイル境界で明確に分割できる場合**かつ Google 共有クォータを過剰消費しない範囲に限る。
- **slice ごとの分離**:
  - 変更対象ファイルが重ならないようファイル境界で slice を切る。
  - Git worktree はファイルを分離するが、ネットワークポートやデータベースまでは分離しない。そのため並列実行時は、**worktree（ブランチ・作業ディレクトリ）だけでなく、使用するポート番号とデータベース名も slice ごとに分ける**（brief に明記する）。
- **join（統合）の手順**:
  1. 全 slice の完了後、統合ブランチへ**依存順にマージ**する。
  2. **各マージのたびに全テストを実行**し、どの統合段階で不整合が生じたか切り分けられるようにする。
  3. slice 間で競合が発生した場合は、**brief の目的・仕様に近い方を残し、採用した理由を報告**する。
  4. join の結果として「マージ順、発生した競合と解決理由、最終テスト結果」を報告し、その統合済み差分をレビュー工程（第 6 節）へ渡す。

## 5. Brief の規則

- すべての委任スレッドは、同じフォルダの `BRIEF_TEMPLATE.md` を用いて brief を作成する。
- テンプレートの必須欄が 1 つでも欠けた brief は発行しない（該当事項がない欄も「なし」または「未確認」と明記する）。
- 前提条件、対象ファイル、対象外、参照すべき根拠、成果物の保存先をすべて brief 内に明記する（理由は 1）。
- 担当モデルは 2.2 と 3 の割り当てから選び、provider と指定理由を書く（Opus / Sonnet の経路は 2.3）。
- 以下の運用パラメータも brief に必ず含める。
  - 機械的な上限と上限到達時の扱い（4.2）
  - `HANDOFF.md` の置き場と書く条件（9.2）
  - 並列 slice の場合の worktree・ポート番号・データベース名（4.3、単一スレッドなら「なし」）
  - レビュー時に適用する `checks` ファイル一覧（8.3、ない場合は「なし」）
  - fallback 先モデル（設定がある場合のみ記入。未確認なら「未確認」、9.2）

## 6. レビューループの規則

- **別ファミリー・read-only の徹底**:
  - レビュアーは、実装者（または起草者）と**別ファミリー**のモデルを割り当てる。
  - レビュアーは **read-only（読み取り専用）** とし、**対象コードやファイルを一切編集・修正しない**。T3 Code 自体はプロンプトや権限モード以上に読み取り専用を強制しないため、brief の対象外・禁止事項に編集禁止を明記し、権限を不必要に広げない。
- **指摘の形式と差し戻し基準**:
  - レビュアーは欠陥を番号付きリストで報告し、各項目に「再現手順・期待動作・実動作・severity（1〜3）」を付ける。対象リポジトリに該当する `checks` ファイルがある場合は必ず通す（8.3）。
  - 実装へ差し戻すのは **severity 1〜2 の指摘だけ** とする（severity 3 は記録に留め、ループを回さない）。
- **修正時のルール（テスト先行）**:
  - severity 1〜2 の指摘を受けて修正する実装側は、**まずその不具合を再現して失敗するテストを書き、その後にコードを修正してテストが通ることを確認**する。
- **再レビューの手順**:
  - 再レビューでは、前回の再現手順を新しい差分に対して再検証し、各指摘を **`FIXED` / `STILL BROKEN` / `NEW REGRESSION`** の 3 区分で判定する。
  - 加えて、**前回試していない攻撃（別の境界条件・異常入力・競合状態など）を 3 つ追加で試す**。
- **終了と上限**:
  - severity 1〜2 の指摘が 0 件になり、適用する `checks` がすべて `PASS` したらレビューループを終了する。
  - 上限に達しても severity 1〜2 が残る場合はループを打ち切る（4.2）。

## 7. 承認の規則

以下の取り消せない操作は、実行前に人間（ユーザー）の明示的な承認を得る。

- ファイル・データ・環境の削除
- 外部への送信・公開
- 支払いに関わる操作
- デプロイ
- マイグレーション

委任先スレッドが上記操作を必要とする段階に達した場合は、操作を実行せずに停止し、対象・実行内容・影響範囲を Muse 経由でユーザーへ報告して承認を待つ。

## 8. 検証の規則

### 8.1 成果物に基づく完了判定

- 作業の完了判定は、スレッドの自己申告ではなく**成果物そのもの**（ファイルの中身、テスト結果、出力数値）で行う。
- Muse は brief の完了条件および検証方法に照らし、成果物と根拠・数値を直接照合する。
- 完了条件を満たしていない場合は完了とせず、不足点を明記して修正または再実行を委任する。

### 8.2 検証への優先投資（Confidence Ladder の考え方）

- エージェントを増員して出力を増やすより先に、**検証の仕組みへの投資を優先する**。検証が弱いまま並列数を上げても、人間の確認がボトルネックになるだけで品質は上がらない。
- PR や成果物が良いという確信を高める基盤として、以下を優先的に整備する。
  - スタック全体を通した**型検査**（コードベース全体を知らなくても安全に変更できる土台）
  - 人間が結果を目視確認できる **preview**
  - エージェント自身が **dev server とテストを起動して自己検証できる環境**（複数ポート等で競合せず実行できること）

### 8.3 文章で書いた検査（checks）

- リンターや型チェッカーでは表現しにくい設計規約・品質基準は、**1 ファイル 1 規則の Markdown ファイル**（例: `checks/<規則名>.md`）としてリポジトリ内に記述する。
- レビュー時には、brief で指定された該当 `checks` ファイルを必ず通し、結果を **`PASS` / `FAIL`** で返させる。`FAIL` の場合は該当箇所を必ず **`file:line`** 付きで報告させる。

## 9. 失敗時と引き継ぎの規則

### 9.1 異常・制限・上限到達時の対処

- **Google クォータ切れ**: クォータ（一定期間内の利用上限）に達した場合、`antigravity-acp` はクレジットへ自動フォールバックせず停止する。Opus / Sonnet は 2.3 に従い切り替え、それ以外の `antigravity` 作業は無理に再試行せず止めて報告し、5 時間枠・週間枠のリセットを待つ。
- **DeepSeek の月枠超過**: 無償枠（2.2）超過によるレート制限時は、他の担当モデルへ振り替える。
- **claudeAgent が使えない場合**: CPA 側の障害等（CPA 503 等）で応答がない場合は、同じ作業を `antigravity` または `acpRegistry_devin` の担当モデルへ振り替え、振り替えたことを報告する。
- **停滞**: 成果物もログも更新されない状態が続く場合は待ち続けず、スレッドを停止して範囲を絞った小さい brief で再発行する。停止判断の目安は、**進捗確認 2 回連続で変化がない状態**とする。ただし Neon のスレッドについては 3.1 の注意に従い、確認間隔を長めに取り、思考時間の長さだけでは停滞とみなさない。
- **上限到達**: 4.2 に従う。
- **マシン停止**: 実行先マシンが停止または到達不能になった場合、Muse が状態と途中成果物を確認したうえで別マシンへ作業を移す。

### 9.2 HANDOFF.md による引き継ぎ

- **別 provider 移動時の前提**: T3 Code でスレッドを別の provider へ移した場合、引き継がれるのは要約のみであり、元のモデルの推論過程やツール呼び出し履歴は引き継がれない。
- **書く条件**: 利用枠の上限や停止が近いとき、または途中で別モデル・別スレッドへ作業を引き継ぐ必要があるときは、完全に停止する前に **`HANDOFF.md`** を書き出す。
- **記載必須の 4 項目**（元のスレッド履歴を参照できない**どのモデルでも `HANDOFF.md` 単体で続きから再開できる粒度**で書く。骨格は `BRIEF_TEMPLATE.md` 付録を参照）:
  1. **済んだこと**: 完了した作業と確認済みの結果
  2. **半端な箇所**: 未完了・途中箇所を必ず**ファイル名と行番号（`file:line`）**で特定して記載
  3. **次の 3 つのコマンド**: 再開者が最初に実行すべき具体的なコマンドを 3 つ
  4. **未決の質問**: 判断待ちの仕様・確認事項
- T3 Code 側の自動 fallback 機能が本環境で実際に利用できるかは**未実測**のため、自動移行に頼らず `HANDOFF.md` と手動の切り替え（2.3、9.1）を基本とする。

## 10. 記録と記憶

- ルーティング規則および運用台帳は、Muse が `t3-agent-ops` スキル（運用手順・台帳を保持するスキル）と作業・進捗ボードに管理する。
- 各スレッド側は brief、成果物ファイル、および引き継ぎ時の `HANDOFF.md` のみを扱い、長期の台帳管理は行わない。
- 通知は `agmsg`（team: `t3-pilot`）の完了通知ブリッジで `muse` 席へ送り、実案件の連絡・引き継ぎはスレッドと成果物ファイル経由で行う。
- 上限到達（4.2）や `HANDOFF.md` による途中引き継ぎ（9.2）は、通常の完了と混同しないよう結果区分を明示して記録する。
