# Brief テンプレート

同じフォルダの `TEAM.md`（チーム運用憲章）と対で使う。初版作成: 2026-11-23。全面改訂: 2026-11-24（詳細版資料の差分を反映）。

## 使い方

- T3 Code（AI エージェントのスレッド管理ツール）経由で子スレッドへ作業を委任する際、以下の骨格をコピーして全欄を埋めてから発行する。
- 子スレッドは親スレッドの文脈を参照できないため、前提・根拠・禁止事項・上限・検証方法・保存先をこの brief（委任指示書）だけで完結させる。
- 欠けた欄がある brief は発行しない。該当事項がない欄も空欄にせず「なし」（または確認前の fallback 欄は「未確認」）と明記する。
- 相談・調査・資料整理など回答文書を求める案件では、作業フォルダに `prompt.md` と `materials/` を置き、成果物を `out/answer.md` に書かせる形式も選択できる。
- 利用枠の上限や停止が近づき途中引き継ぎが必要になった場合は、末尾の「付録: HANDOFF.md の骨格」に従って `HANDOFF.md` を出力させる。

## コピー用テンプレート

```markdown
# <タイトル>

## 目的と背景
- 何を達成するか:
- 背景・現在の状況:

## 完了条件
- [ ] <検証可能な条件 1（例: 特定ファイルの作成・更新、テストコマンドの成功）>
- [ ] <検証可能な条件 2（例: 確認コマンドと期待出力）>

## 対象ファイル・範囲
- 作業ディレクトリ: ~/agentic-project/<対象ディレクトリ>
- 対象ファイル:
  - <パス 1>
  - <パス 2>
- 並列 slice 分離（並列実装を行う場合のみ記入。単一スレッドならすべて「なし」）:
  - worktree（ブランチ名・作業パス）: <例: branch `t3/feat-api`, worktree パス / 単一スレッドなら「なし」>
  - 割り当てポート番号: <例: 3101 / なし>
  - データベース名: <例: app_slice_api / なし>

## 対象外・やってはいけないこと
- 変更してはいけないファイル・範囲:
- 禁止事項（例: 承認なしの削除・外部送信・支払い・デプロイ・マイグレーション、認証情報の記載）:

## 根拠
- 参照するファイル・ログ・数値:
  - <パスや記録箇所>

## 制約
- 対象マシン: <例: gpu-01 (100.105.219.77)>
- provider（モデル実行基盤の接続先種別）・モデルと指定理由: <例: acpRegistry_devin / gpt-6.2 sol（実装の担当モデルのため）>
- fallback 先モデル（利用枠で止まった場合の代替。本環境で自動 fallback が動作するかは未実測のため、設定がある場合のみ記入し、未確認なら「未確認」と書く）: <設定済みのモデル名、または「未確認」>
- クォータ（一定期間内の利用上限）配慮: <例: Google 共有クォータ（5時間枠・週間枠）を過剰に消費しないよう並列展開しない / DeepSeek は月 3,000 リクエスト無償枠内で使用>
- 機械的な上限:
  - レビュー上限: 最大 3 ラウンド
  - エージェント間受け渡し上限: 人間を挟まず最大 4 回
- 期限・目安: <期限、または「指定なし（進捗確認 2 回連続で変化がない場合は停止対象）」>

## 手順
- 固定手順（必ずこの順で実施する事項）:
  1. <手順 1>
  2. <手順 2>
  - （並列 slice を統合する join の場合: 統合ブランチへ依存順にマージし、各マージ後に全テストを実行する。競合時は brief の目的・仕様に近い方を残し理由を報告する）
- 裁量範囲（実施方法を受託側に任せる部分）:
  - <任せる範囲を明記。ない場合は「なし」>

## レビュアー
- 担当 provider・モデル（計画・実装と別ファミリー、read-only・編集禁止）: <例: 実装が Claude 系や grok-4.7 等の場合は acpRegistry_devin / gpt-6.2 sol または gpt-6.2 astra。実装が gpt-6.2 sol の場合は別ファミリーの antigravity / claude-opus-5-5（クォータ切れ時は acpRegistry_devin の claude opus 5.5）>
- レビュー観点とループ規則:
  - 観点: <例: 完了条件との一致、事実・数値の正確性、対象外ファイルへの非干渉>
  - 運用: read-only で編集しない。指摘は再現手順・期待動作・実動作・severity（1〜3）付きで返し、severity 1〜2 のみ実装へ戻す（修正時は失敗するテストを先に書いてから直す）。再レビューでは前回の再現手順を `FIXED` / `STILL BROKEN` / `NEW REGRESSION` で判定し、前回試していない攻撃を 3 つ追加で試す。最大 3 ラウンドまで。
- 適用する checks ファイル一覧（1 ファイル 1 規則の Markdown、`PASS` / `FAIL` + `file:line` で判定）:
  - <例: `checks/error-handling.md` / 対象がない場合は「なし」>

## 検証方法
- Muse が完了判定に用いる確認手順:
  - <成果物ファイルの内容確認、テストコマンド結果の照合、`checks` 判定結果の確認、数値突合など。自己申告では判定しない>

## 失敗時の扱い
- 停止条件:
  - クォータ切れ、CPA 503、進捗確認 2 回連続で成果物・ログに変化なし、承認が必要な不可逆操作の発生、対象マシンの停止
  - 機械的な上限への到達（レビュー 3 ラウンド到達、または人間を挟まないエージェント間受け渡し 4 回到達）
- 上限到達時の報告形式:
  - **「完了」「成功」とは書かず、必ず結果区分を「上限到達」として報告する。** 到達したラウンド数／受け渡し回数、未解消の指摘・残課題、判断を仰ぐ論点を明記して人間へ上げる。
- その他の失敗・停止時の報告形式:
  - 発生事象、到達済み箇所、未完了箇所、エラー出力または状態、推奨する次の手を成果物またはスレッド末尾に簡潔に記載して停止する。
- `HANDOFF.md` の置き場と書く条件:
  - 置き場: `~/agentic-project/<対象ディレクトリ>/HANDOFF.md`（不要な極小タスク等で省略する場合は「なし」と明記）
  - 書く条件: 利用枠の上限や停止が近いとき、または別モデル・別スレッドへ途中引き継ぎが必要なときは、止まる前に末尾付録の骨格どおりに `HANDOFF.md` を書く（別 provider 移動時は要約しか渡らないため、単体で再開できる粒度にする）。

## 成果物の置き場
- 成果物パス: <例: ~/agentic-project/<対象ディレクトリ>/<成果物ファイル>>
- 引き継ぎファイル（発生時）: `~/agentic-project/<対象ディレクトリ>/HANDOFF.md`
- （相談・資料型の場合の選択形式）入力を `prompt.md` + `materials/` に配置し、回答を `out/answer.md` へ出力する。
```

## 記入例

以下は、リポジトリの `README.md` にセットアップ手順を追記する小タスクの記入例である。

```markdown
# README.md へのセットアップ手順追記

## 目的と背景
- 何を達成するか: 対象リポジトリの `README.md` に、`uv`（パッケージおよび環境管理ツール）を用いたローカル環境のセットアップ手順を追記する。
- 背景・現在の状況: 現行の `README.md` にはリポジトリ概要のみが記載されており、新規参加者が依存関係を再現する手順が不足している。

## 完了条件
- [ ] `README.md` に前提条件、依存関係インストール手順（`uv` コマンド）、動作確認コマンドの 3 項目が追記されている。
- [ ] 記載したセットアップ手順が `pyproject.toml` の定義と矛盾していない。
- [ ] `git diff --stat` で変更対象が `README.md` のみであることを確認できる。

## 対象ファイル・範囲
- 作業ディレクトリ: ~/agentic-project/<対象リポジトリ>
- 対象ファイル:
  - `README.md`（編集対象）
  - `pyproject.toml`（参照のみ）
- 並列 slice 分離:
  - worktree（ブランチ名・作業パス）: なし（単一スレッドで実行）
  - 割り当てポート番号: なし
  - データベース名: なし

## 対象外・やってはいけないこと
- `README.md` 以外のファイル（ソースコード、`pyproject.toml`、ロックファイル等）を変更しない。
- ファイル削除、外部への push・送信、支払い、デプロイ、マイグレーションなど取り消せない操作を行わない。
- 根拠のないコマンドオプションやバージョン番号を補完しない。
- 認証情報や個人トークンを記載しない。

## 根拠
- 対象リポジトリ直下の `pyproject.toml`（Python 要件および定義済みスクリプト）
- 既存の `README.md`

## 制約
- 対象マシン: `gpu-01` (`100.105.219.77`)
- provider・モデルと指定理由: `antigravity` / `gemini-4-neon`（文書の起草・構成を Gemini 系が担当する標準分担のため）
- fallback 先モデル: 未確認（本環境で自動 fallback が動作するか未実測のため）
- クォータ配慮: Google 共有クォータ（5時間枠・週間枠）を消費するため、不要な再実行や並列展開を行わない。
- 機械的な上限:
  - レビュー上限: 最大 3 ラウンド
  - エージェント間受け渡し上限: 人間を挟まず最大 4 回
- 期限・目安: 指定なし（進捗確認 2 回連続で変化がない場合は停止して再分割）

## 手順
- 固定手順:
  1. 既存の `README.md` と `pyproject.toml` を読み取り、記載済みの依存関係と実行コマンドを確認する。
  2. `README.md` に「セットアップ」節を追加し、手順を追記する。
  3. `git diff --stat` および `git diff README.md` を実行し、変更範囲と記載内容を確認する。
- 裁量範囲:
  - 見出し階層と箇条書きの表現は既存の `README.md` の書式に合わせて調整してよい。

## レビュアー
- 担当 provider・モデル: `antigravity` / `claude-opus-5-5`（起草の Gemini 系とは別ファミリー、read-only・編集禁止。Google クォータ切れの場合は `acpRegistry_devin` の `claude opus 5.5` を使用）
- レビュー観点とループ規則:
  - 観点: `pyproject.toml` との整合性、未記載コマンドの混入有無、対象外ファイルへの非干渉
  - 運用: read-only で編集しない。severity 1〜2 の指摘のみ起草側へ戻し、再レビュー時は前回指摘を `FIXED` / `STILL BROKEN` / `NEW REGRESSION` で判定する。最大 3 ラウンドまで。
- 適用する checks ファイル一覧:
  - なし（対象リポジトリに文書用 `checks/*.md` が存在しないため。存在する場合はここにパスを列挙する）

## 検証方法
- Muse が以下を直接確認して完了を判定する。
  - 更新後の `README.md` の本文と `pyproject.toml` の記述の照合
  - `git status --short` および `git diff --stat` で変更が `README.md` のみであることの確認

## 失敗時の扱い
- 停止条件:
  - `pyproject.toml` から必要な起動手順が特定できない場合
  - クォータ切れ、または進捗確認 2 回連続で成果物・ログに変化がない場合
  - レビュー 3 ラウンド到達、または受け渡し 4 回到達の場合
- 上限到達時の報告形式:
  - 「完了」「成功」と書かず、結果区分を「上限到達」と明記し、到達ラウンド／回数と未解消点を添えて人間へ報告する。
- その他の失敗・停止時の報告形式:
  - 発生事象、確認済みファイル、不足情報、次の対応案をスレッド末尾に箇条書きで報告して停止する。
- `HANDOFF.md` の置き場と書く条件:
  - 置き場: `~/agentic-project/<対象リポジトリ>/HANDOFF.md`
  - 書く条件: 利用枠の上限や停止が近づいた場合、または別モデルへ途中引き継ぎが必要になった場合、停止前に付録の骨格どおりに作成する。

## 成果物の置き場
- 成果物パス: `~/agentic-project/<対象リポジトリ>/README.md`（既存ファイルへの追記）
- 引き継ぎファイル（発生時）: `~/agentic-project/<対象リポジトリ>/HANDOFF.md`
```

## 付録: HANDOFF.md の骨格

T3 Code 上でスレッドを別 provider へ移すと要約しか渡らず、元のモデルの推論過程やツール呼び出し履歴は引き継がれない。利用枠の上限や停止が近いときは、止まる前に以下の骨格で `HANDOFF.md` を書き、**どのモデルであってもこのファイル単体だけで続きから再開できる**状態にする。

```markdown
# HANDOFF.md

- 対象タスク・brief: <タスク名または brief のパス>
- 停止理由: <例: Google クォータ上限接近 / DeepSeek 月枠到達 / 別モデルへ引き継ぎ>
- 作業ディレクトリ・ブランチ: <例: ~/agentic-project/<dir>, branch `t3/...`>

## 1. 済んだこと
- <完了した作業 1（確認済みテスト・コマンド結果があれば簡潔に付記）>
- <完了した作業 2>

## 2. 半端な箇所（ファイル名と行番号）
- `<path/to/file1>:<line>` — <どこまで実装・修正済みで、何が残っているか>
- `<path/to/file2>:<line>` — <同上>

## 3. 次の 3 つのコマンド
1. `<再開直後に状態や差分を確認するコマンド>`
2. `<半端な箇所の検証・テストを実行するコマンド>`
3. `<次に進めるためのビルド・確認・実行コマンド>`

## 4. 未決の質問
- <判断待ちの仕様・確認事項 1（ない場合は「なし」）>
- <判断待ちの仕様・確認事項 2>
```
