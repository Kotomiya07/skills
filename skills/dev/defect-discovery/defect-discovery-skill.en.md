# Full Code Audit (Defect Discovery for General Code)

A procedure for systematically discovering latent defects in an existing codebase. Separate from security auditing (which specializes in CWE classes), it targets general defect classes: state transitions, races, persistence, numerics, unbounded growth, idempotency, and the like. Its core pattern comes from large-scale code audits in production practice, extended through a thorough survey of defect-discovery methods checked against published empirical research.
Structure: a "common core" that applies regardless of mode (Steps 0–7 and the reporting format), plus mode-specific procedures for diff review (Mode 1) and full-codebase inspection (Mode 2). Declare which mode applies when starting, and apply the common core together with that mode's section.

## When to use

- When the requester asks for a code audit, a full audit, or a check for latent defects. Start with this procedure regardless of scale.
- Empirical premise: static close reading alone finds only the classes that "can be traced by reading"; problems that surface in production (state transitions, timing races) came from outside the coverage of close reading. The overlap between methods' findings is small (Project Zero measured 25% overlap between agent auditing and fuzzing), so design the audit as a combination of multiple methods, and state in the report which methods were not used.
- Calibrating expected yield: inspection by reading has a yield that skews by defect type (it catches surface-level logic errors but rarely deep, macroscopic defects; in Microsoft's empirical study, only about 14% of review comments touched defects at all, and the binding constraints were understanding and familiarity). Therefore do not use a passing audit as evidence that no deep defects exist; state explicitly that detection of deep defects is assigned to dynamic verification (Step 5) and invariants (Step 6).

## Common core (applies to both modes)

Steps 0–7 and the reporting format below apply to both Mode 1 and Mode 2. Mode-specific provisions are in each mode's section further down.

0. **Tracing behavior (the main axis)**: The first pass of a diff review or final check reads every changed line for understanding. For each change, answer — tracing forward through its connections to unchanged code — how the change alters the behavior of the assembled system as a whole: what stops happening / what stalls permanently if which input or response never arrives / what the progress of the core function (what must always keep advancing in this system) has come to depend on. Defects appear not in the changed line itself but as properties of the chain "change × unchanged code", so line-level classification cannot in principle see them. The class matrix (Step 2 below) is an auxiliary sweep for known recurrences, run after this main axis; it is not used to define coverage. Do not call an inspection that has not passed through this main axis a "full-codebase inspection" (it is in substance an extraction check, and the report must name it as such).
   Context building and the expectation model: before starting to read, write an "expectation model document" (the purpose of the change, the behavior before the change, the behavior expected after the change, and the range within which divergence from the ideal form is acceptable). Read against this document. Build the expectation model from the specification, the contracts, and the pre-change behavior — not from how well-typed the code surface looks. Record an understanding scope for each range in the ledger (Full / Focused / Partial / Shallow), and fold Shallow ranges (judged by relying on automated tests passing or on someone else's confirmation) into the unverified range in the report.
   Independence: for release-scale diffs, a fresh context (another reviewer or an external model) performs the first pass of the main axis before the owner's own check, and the owner adjudicates its findings. Reading your own work product in your own context narrows the field of view through investment in its conclusions, so do not use it for the main axis. Independence and familiarity are separate axes and both are required: if the first-pass reviewer is unfamiliar with the target, place a comprehension phase as an independent deliverable before adjudication (a summary of the target's structure, core functions, and normal behavior, confirmed by the adjudicating side before the first pass begins). Record in the ledger, as a caveat, that a first pass by an unfamiliar reviewer yields only "obvious defects".
   Defining the population: the population of a diff review or final check is the entire diff (all functional areas). The event that triggered the inspection decides only the first question; it does not pull the population toward its own lineage. Splitting areas is only for dividing tracks; it is never a ground for exclusion. Always record the population definition in the ledger (what was included / what was excluded and why), and report any inspection with excluded ranges as limited in coverage.
   Reading discipline: rules that keep the main-axis reading from being abbreviated at any point. An affirmation ("as intended", "reasonable", "correct", "sound", "no impact") may be issued only for a point that has passed the questions below. Empirical background: on the same diff, an inspection that actually read the relevant points still missed about half of the confirmed defects, and most of those were cases of "read it and concluded there was no problem" or "found a different defect at the same point and closed the examination".
   - **The endpoint of an affirmation**: when you want to affirm, concretize one minimal execution (input, execution order, history) under which the affirmation would be false, and read until the guarantee in the code excludes it. Writing a caveat ("non-atomic, but…", "under this assumption…") does not finish verification; determine whether the counterexample stands as a legal execution, and what constraint excludes it. Do not promote the correctness of types, syntax, and exception handling (local correctness) into the establishment of the promised result (global correctness).
   - **Round trips of values across boundaries**: when a value, reference, or stored artifact crosses a boundary (module / scope / process / clock / version or generation), reconcile the meaning the producing side guarantees with the meaning the consuming side requires. Trace comparisons backward along both sides' origins and transformation paths, and ask whether the same reality takes the same value on both sides. For rejection by comparison against a constant, verify — by the inclusion between the set of values the producer can legitimately create and the set the reader accepts — whether the constant is a contractual constraint or merely a default or operational setting. Trace references not to "whether they can be read if present" but to whose assignment, in which scope, actually delivers the live entity. Trace identifiers and hashes backward to their ingredients, not only to their uses, and ask whether the ingredients include values that change under conditions that must not change them (relocation, restart, environment).
   - **Failure directions of added lines**: for each added expression, operation, or call, ask separately: (i) can the expression itself complete evaluation (is it computable over the entire domain of values the input side accepts — being acceptable does not imply being computable), (ii) what remains when a side effect fails at each stage — not yet executed, partially established, established, (iii) do the return value and exceptions agree with the state that actually came to hold (has a failure in post-success cleanup inverted an established success into a failure), (iv) how the remaining state will be interpreted at the next observation (caller, another actor, the next run, the entry point after a restart). After examining one failure direction, leave the opposite direction and independent properties explicitly marked "unexamined"; do not count them as examined. When a dynamic experiment does not observe an event, ask not whether the number of trials was increased, but whether the execution order that produces the event was forced (e.g., stopping immediately after a boundary and injecting the failure of another actor's execution or of subsequent processing only).
   - **Between observation and action**: for a change that decides release, deletion, or certification from multiple observations, insert a start, a completion, and a move, one at a time, between each pair of observations and between the last observation and the action, and ask whether the judgment still holds. "Do nothing when unknown" does not prevent misjudgment from an old observation that was obtained.
   - **Irreversibility of deletion, release, and fixation**: for a change that deletes a request, releases a resource, fixes a classification, or removes a recovery path, ask what is lost if that judgment was wrong, and whether it can be corrected. When fulfillment is delegated to another process, trace to the terminal point that deletes the request and confirm whether the deletion condition requires proof that the content has been reflected. When deleting an adaptation, read separately whether the target's nature is invariant and whether the first observation was correct, and ask whether the sequence of failures the old version could recover from can still be recovered in the new version. For sets and ledgers that hold state, ask not only about the correctness of additions but also about when an element may be forgotten and the path by which it is actually forgotten (its lifetime).
   - **Acceptance of artifacts (the writer–reader round trip)**: for save/restore changes, read one full cycle — normal operation → save → restore → continue — and ask whether the reader accepts everything the same version's writer can produce, and whether work can continue with the same meaning after restore. When acceptance conditions have become stricter, pass artifacts produced under the old version's generation rules (including accumulated, multi-generation history) through the new version's reader, and verify acceptance and preservation of meaning. Do not conclude "no impact" from merely confirming that a consumer of the new format exists.
   - **Mechanisms that depend on future execution**: for retry, recovery, and deferred execution, verify until one concrete execution sequence can be composed that returns from the failed state to the intended processing. Collect the necessary conditions backward from the target branch to the entry point, trace laterally every path that rewrites the state those conditions read, and ask whether the sequence remains reachable with normal periodic updates in between. Do not equate "the state for retry is saved" with "the retry will execute".
   - **Termination and late arrivals**: for a change that terminates a request by cancellation or timeout, ask what pending items, reservations, and commit authority remain, and trace whether that termination is also respected on the processing side of events that arrive later.
   - **Changes to tests**: for a change to an expected value or a comparison condition, ask "which behavior that used to fail now passes", and reconcile it with the test's name and the specification's promise. For a change that replaces real processing with a fake, ask whether the facts the fake supplies as premises are themselves what the test is meant to prove, and whether another test carrying the same guarantee remains.
   - **Propagating the question, and self-review**: when you detect one defect, extract not the defect itself but the question that found it, and reapply that question to every location with the same structure (a countermeasure against uneven detection across locations). After reading, line up not only the list of findings but also "the paths actually traced" and "the connections not yet confirmed", interrogate the blank spots, and if there is a bias, reverse direction (producer ↔ consumer, normal path ↔ abnormal path, current version's artifacts ↔ old version's artifacts) and read again.
   Reading discipline, supplement 1: misses of the affirmation-cleared type persist in altered form even in re-inspections that apply the discipline (covering sibling locations with the same lineage's conclusion / affirming a group in bulk / closing a different proposition with the current consistency of a record and a passing verification), so fix the unit of affirmation and the completion conditions for reading.
   - **Distribute questions, not conclusions**: when you obtain a finding of a given lineage, do not reuse its conclusion in evaluating sibling locations; reapply the question at each location, and do not mark a location confirmed until location-specific grounds exist (the origins and transformations of both sides, the actual existence of the binding, and so on). "Same lineage" is recorded as a relation; it is not an evaluation result. Findings may be merged into one entry; inspection units may not.
   - **Second-pass failure-direction reading**: after reading the semantics of a changed point, regardless of whether a finding emerged, re-read the same lines and the same function using only failure-direction questions (failure of evaluation / partial effect / where the exception goes / the next observation). The more strongly the first pass produced a finding at a point, the more independently the completion of the second pass must be recorded there; do not reuse a semantic finding as grounds for having confirmed the failure direction.
   - **Group affirmations are per element**: grouping changes is for display only; issue affirmations per element. For each element, confirm its grounds of establishment (its source / the path by which the value enters / where it arrives / its handling on failure); if even one element is unevaluated, record the group as "partially unevaluated". Being read-only or exception-safe is not proof that wiring is established. For wiring that swallows exceptions, do not affirm establishment until grounds exist that the function manifests at least once on the normal path.
   - **Authority grounds for deletion, release, fulfillment, and certification**: for processing that deletes, releases, fulfills, or certifies something, ask: "what is the fact that makes it right to perform this operation now, and where, for this target, was that fact confirmed?" The name of the processing ("fulfill", "certify", etc.) is not treated as proof. In a design that leaves the guarantee to the caller or to another process, trace whether the guarantee holds on every reachable path, and check whether a concrete case of the condition not holding (an unfulfilled request, an artifact of another generation, etc.) can be made to reach the operation point. When certifying from multiple artifacts, ask — separately from whether each artifact is individually valid — about the binding that they belong to the same target, generation, and execution.
   - **Separating existence judgment from impact evaluation**: when you identify a mechanism by which a divergence from expectation arises, first fix and record the existence judgment (the conditions of occurrence, the mechanism, the divergence from expectation, the grounds), and place impact evaluation and the response decision in a separate field as a separate judgment. "The impact is small" and "no actual harm has been confirmed" are not reasons to rewrite an existence judgment into "no problem"; in such cases, leave the item as "defect present, low priority (with impact evaluation)".
   - **Two questions for records and evidence**: when reading a record or evidence, ask separately about "agreement with the current actual object" and "the truth of the past the record claims (as of when, about which actual object)". For a change that alters the binding target (reference, hash, storage location) while keeping the date, result, and provenance, confirm the grounds on which that date and result may be attributed to the new binding target. When only current agreement has been confirmed, record "current agreement confirmed only; provenance unconfirmed", and do not treat it as both confirmed.
   - **Coverage of verification**: when a verification or cross-check passes, record separately "there is no violation among the enumerated targets" and "all necessary targets have been enumerated". Build the necessary set independently — from actual dependencies, calls, and input reads, not from the list of targets under verification — and confirm its inclusion in the target set. Do not let another verification's or another lock's passing fill in a shortfall in this coverage.
   - **Scope of declared rules**: when using a comment, a docstring, or a rule statement as grounds for affirmation, separate the declared intent from the grounds for applying it to the present conditions. Confirm the processing stage, failure conditions, and ordering in effect when the rule was established; if the diff introduces new failure points or orderings, ask what is now returned, what remains, and what can be retried for inputs and environments that used to succeed, and do not absorb new conditions into the generality of the wording.
   - **Lifetimes of retained things (remove the role name)**: when reading a set whose purpose is retention (deduplication, history, caches, etc.), ask — separately from the order of additions and consumption — "how many times can a unique element grow, when does it become unnecessary, who reclaims it, and what determines the upper bound of the retained volume?" If no bound can be shown, record "boundedness of retained volume unproven". Read retention and deletion changes with the role name removed, and check both directions: deletion too early and deletion too late (unbounded retention).
   Reading discipline, supplement 2: the types in which an affirmation is obtained by "searching for supporting material" (an existence check turning into a survival check), trust in declared contracts, and suppression at the entrance of recording by impact evaluation also persist, so fix the procedure of affirmation itself.
   - **Affirmations are obtained with a verification record**: for each claim you want to affirm, record "the claim / the forward trace (generation and assignment → propagation → branching → consumption and observation) / the search for a counterexample (a configuration in which the claim is false even if all supporting material exists) / the conclusion and the unconfirmed points". The existence of a referent, a delegate, or a registration target is scaffolding for the search, not grounds for affirmation. Trace wiring from the actual place of generation through assignment, lifetime, and observation, and confirm identity of scope and object, not merely of name. Build the necessary set for coverage independently of registries and lists, and reconcile it against the target set mechanism by mechanism ("it is registered somewhere" is not a passing condition). For delegation, trace each of the normal, nonexistent, rejected, and runtime-failure cases through capture, transformation, the caller's branching, and the final behavior (do not stop the trace at "it throws an exception"). For aggregate values, line up the global condition and the per-element conditions, and confirm whether a per-element rescue can actually override a global rejection (including whether that branch is reachable). "The stricter side" is not synonymous with "the correct side".
   - **The changed-function ledger and refutation of contracts**: build a complete ledger of the functions newly added or changed in the diff (do not target only the functions that caught your interest), and record each function's contract as a proposition (accepted inputs, handling of rejection, the range of return values, exceptions permitted to leak, the invariants it maintains; docstrings and comments are treated as sources of propositions, not as evidence). Then inventory the operations in evaluation order (additions, transformations, comparisons, references, and calls executed before conditions, including the scope of short-circuit evaluation and exception capture), derive boundary inputs from the types and operations (empty, minimum and maximum, immediately before / exactly at / immediately after a boundary, combinations whose operation results exceed the representable range), and evaluate them. The completion condition is that every row of the ledger has "contract / boundary cases / result" filled in; a blank is incomplete.
   - **Automatic registration of divergence statements**: at the moment you write, in the course of reading, a sentence of the form "under condition X, the implementation does Y, while the contract or expectation Z requires W", register it as a finding. Registration is distinct from confirming a defect; impact evaluation and the response decision go in the disposition field after registration. Closing an item as not-a-defect requires one of: a refutation of the mechanism, a correction of the contract interpretation, or grounds that it is permitted by specification; smallness of impact alone does not close it.
   - **Read condition changes as differences of acceptance sets**: read a change to a condition, a boundary, or an acceptance range as the difference between the old condition's acceptance set and the new condition's acceptance set (the set of newly permitted things), split by the configurations relevant to the judgment and to downstream invariants. For each configuration, construct a minimal newly-accepted example, an extreme newly-accepted example (distance, count, time difference, and density pushed to the maximum the range allows), a composite example, and an example aimed at breaking a subsequent contract (completeness, continuity, ordering, etc.). When relaxing a property the old condition guaranteed, confirm the grounds that the property is no longer needed, or the grounds that an alternative check maintains it. Do not complete the item on the success of the representative case the change describes.
   - **Establishment conditions of mandatory operations**: extract from the diff not only added operations but also the making-mandatory of optional operations, the removal of fallbacks, and added rejection conditions (the trigger is not a classification of the environment but the fact itself that a new mandatory dependency has arisen), and for each record "the required capability (the conditions on the counterparty side and the environment side needed for establishment) / the grounds of establishment (where it is guaranteed) / the path when the capability is absent (which of: an alternative, an explicit rejection, an unrecoverable stall) / the effectiveness of retry (the distinction between conditions that retry changes and conditions that do not change unless the environment changes)". An item for which neither the grounds that the premise is guaranteed nor the permitted behavior when the premise fails can be shown is not closed as "environment-dependent but fine"; leave it unconfirmed.
   - **Lifetime inspection of retained things (separated from functional inspection)**: ledger every new or changed mutable set or accumulation, regardless of the change's theme or name (existing retained things are also in scope when their addition or reclamation conditions change). For each, record the owner and its lifetime, the conditions for adding elements, the semantic lifetime (the period over which future judgments need to refer to it), the actual retention lifetime (the period until removal), the paths of deletion, replacement, and full clearing and their reachability, and the growth over long operation or its upper bound. Split the inspection into two columns: functional inspection (whether the intended judgment or suppression works correctly by virtue of the retention) and lifetime inspection (whether elements that have become unnecessary are reclaimed, and whether the retained volume is constrained to a justified range). Do not complete the item until both columns have independent grounds. When keys belonging to a short-lived unit (a run, a generation, a session, etc.) are placed on a long-lived owner, always trace the transitions across that unit's end.
   - **Follow what comes after a committing event**: for changes involving publication, registration, or commitment, trace the identity of the entity, not the name. Build an entity-correspondence map (which entity each name, reference, and handle denotes; whether it is a copy or another path to the same entity) and a post-commitment change-path table (for remaining aliases, open handles, and shared references: who can change them, until when), and trace whether the next execution, a retry, concurrent processing, or cleanup reuses or alters those paths. The scope of tracing is not up to the return of the committing function, but the period over which the contract requires the content to be preserved. Do not judge, from the deletion of a name alone, that the ability to change through existing handles has also been lost.
   - **View reachability together with the normal path**: when reading a retry, recovery, or cleanup mechanism, decompose the entry conditions into predicates over state variables, time, generation, and the like; reverse-lookup the writers of each element, including normal processing; and lay the updates and the entry judgment out in one cycle's execution order. Then, starting from "a state in which recovery has become necessary", trace several cycles without omitting normal processing, and confirm whether the entry conditions can really be met, and whether another path changes the conditions first. Do not treat the satisfaction of an entry condition (such as freshness) as evidence that unfinished processing has completed.
   - **Reconcile wording as a set of claims**: decompose a change to documentation, guidance, or display text not as a set of names but as a set of claims (who does what, to which stage it is complete, what is confirmed and what is unconfirmed, what the user is told they may do next), and map each claim to the implementation's transition conditions, observed facts, and guarantees. Then run a counterexample search: "even if this state is reached, is there an execution under which this wording's claim is false?" Confirming the existence of an identifier is confirming a referent; it is not confirming the correctness of the wording.
   The dependency ledger: paired with the changed-function ledger, build a dependency ledger. For the unchanged functions and classes that the change references, write a summary of their contracts in declarative short sentences (accepted inputs, return values, state changes, exceptions, identity of scope and entity) and fix them as the premises of adjudication. Its purpose is to localize, before reading, information that adjudication needs and that is otherwise scattered across the whole system. Its completion condition is the same as the changed-function ledger's (a blank is incomplete).
   Reading order: the second pass (the failure-direction reading) is read in the reverse order of the first pass, or in order of closeness to the core of the change. Record in the ledger the order read and each range's position (first half / second half), and whether ranges positioned in the second half became subjects of the second pass (based on the empirical finding that detection drops toward the end of the presentation order).

1. **Mechanical enumeration of the population (hybrid exhaustive sweep, auxiliary)**: build the audit population by mechanical enumeration, not by human attention. Enumerate exhaustively — by grep / AST-style listing — the target files and modules and the candidate locations for each defect class (exception handling, retries, state writes, numeric computation, unbounded growth, time dependence, and so on), and keep the actual output in the audit ledger. The LLM's role is close contextual reading of the enumerated candidates; it does not substitute an impression of reading for the enumeration itself. Do not settle a huge file with the caveat "extraction reading"; cover it by enumeration → close reading per candidate. The enumeration trust loop: for enumerated and analyzed candidates, the adjudicating side records a "useful / noise" evaluation in the ledger, and enumeration patterns with a high noise rate are revised or retired. Enumeration output is a lower bound of the population; not appearing in an enumeration is not evidence of absence. State in one line in the ledger "the range the enumeration may miss (false negatives)".
   Mechanical enumeration of the targets of the questions: the questions of the reading discipline leak as long as their targets are chosen by attention. Mechanically enumerate the following targets from the diff exhaustively, apply the corresponding question to each without exception, and record a disposition (a finding / an affirmation with a verification record / an explicit "unverified"). The audit is not complete while any target lacks a disposition. (i) Evaluation expressions: the arithmetic, comparison, and conversion expressions appearing in changed validation and computation — for each, "can evaluation complete over the input side's entire accepted domain and at boundary inputs (maximum, minimum, exactly at a boundary)?" (ii) References: globals(), attributes, name resolution, imports, registry lookups — for each, "by whose assignment, in which scope, does the entity arrive (down to the classification of the assigning side's scope)?" (iii) The target sets of locks, registries, and verifications — for each, "does it agree with the necessary set built independently from dependencies and calls (coverage)?" (iv) The rejection conditions of verification functions: every comparison against a constant, type condition, and required field — for each, "is the set of values the producing side can legitimately create not rejected by this condition?" (v) Retained sets: new or changed sets, ledgers, and caches — for each, the lifetime inspection (the two columns of the lifetime inspection of retained things). Keep the enumeration's actual output in the ledger. Recording in the ledger is not registration of a finding: when, for an enumerated target, you identify "a state that diverges from the contract", register it as a finding at that point. Perform impact and risk evaluation only in the finding's disposition field; do not substitute for registration by placing "surrounding circumstances", "low risk", or "on the safe side" in the ledger or in a verification record.
   The form gate for disposition records: each enumerated target must have its own independent disposition line (folding it into another finding or verification record is prohibited). A disposition line counts as "disposed" only when it carries the form of evidence its question type requires. (i) Disposition of a reference: an enumeration of the binding's assignment locations, or the result of resolution by execution, is mandatory; an affirmation by static reconciliation alone does not count as a disposition. (ii) Disposition of a rejection condition: the result of evaluating that condition alone at boundary inputs is mandatory; the evaluation result of a different condition of the same function is no substitute. (iii) Disposition of a retained set: an enumeration of the addition locations and the deletion locations is mandatory; the absence of a deletion location is itself registered as a finding (it is not made an object of "left unverified"). (iv) Questions of existence (whether a binding, a deletion path, or a reachability path exists) can be settled from the code, so a hold of "no material, therefore unverified" is not accepted as a disposition. What may be left unverified for lack of material is limited to questions that depend on the actual existence of a real environment or real artifacts. (v) Disposition of coverage: the result of building the necessary set independently — from actual dependencies, calls, and input reads, not from the list of targets under verification, a registry, or a lock table — and confirming its inclusion in the target set is mandatory. Confirming agreement between recorded values and actual objects (including hash and byte agreement) is evidence for a different question and does not count as a coverage disposition.
2. **The defect-class matrix**: fix the population by class in advance. At minimum: waits and retries with no exit condition / swallowing of exceptions and mixing of heterogeneous failures / missing validation of configuration value ranges (missing keys, negative values, NaN, type mismatches) / unbounded growth (logs, lists, retention) / numeric instability (float ordering, repr dependence, rounding) / missing idempotency and windows of double application / persistence consistency (atomic writes, fsync, integrity on restore) / undefined cells of state transitions (combinations of state × event that are nowhere written) / freshness and time dependence (handling of staleness, mixing of still-forming data) / divergence between display and actual state.
   Rules for using the matrix: (i) do not use the items as a checklist to be checked off; convert each item into a scenario-shaped question ("construct one concrete execution under which this defect type holds in this target") and assign an owner (a track / a viewpoint) to each item before use. (ii) Add and revise items from your own organization's actual defect history; do not transplant external general-purpose lists wholesale. (iii) The matrix is a memory aid, not a definition of coverage.
3. **Track division and parallel execution**: split the target and run the tracks in parallel (the main body / the integration layer / the operational parts, etc.). Each track receives the enumeration results for its assigned range as input. The union of independent multiple passes is the standard form: for release-scale audits, read the same population at least twice, with independent first passes of different viewpoints, and take the findings as the union of both passes. Each pass completes without seeing the other pass's findings, and the integrating side resolves duplication and adjudicates disagreements. When one pass closed a target as "no problem" or by a ledger record and the other pass turns it into a finding, treat the finding side as correct for that target, and record the closed side's grounds as adjudication material (do not erase it by majority vote). Skeptical re-review of affirmative dispositions: after the union is fixed, an independent skeptic takes only the integrated "no problem" dispositions and their verification records as its target, and for each affirmation attempts a refutation starting from "if this affirmation were wrong, under which input or state would it break?" The re-review does not count an affirmation's grounds (statements of intent, protective mechanisms, confirmation of the success path) as grounds; an affirmation can be maintained only by refutation attempts (fault injection, state synthesis, boundary inputs). Register a refuted disposition as a finding, and distinguish a maintained disposition as "re-reviewed". In the division, assign each track, in addition to a range, one viewpoint (user / operator / attacker / future changer / downstream user), and record it in the assignment table. A composition whose viewpoints duplicate is treated as overlapping coverage even if the areas differ. The start condition for the first pass is "the material and context are in place" (a readiness criterion), placed at the head of the assignment table. How to cut chunks: split the amount read in one reading session into units that can be cut before the detection rate starts to fall (as a guide, a reading amount equivalent to 60–90 minutes), and cut at dependency closures (the target and the units it directly references and is referenced by), not at file boundaries. For ranges spanning sessions, re-read the latter part of the previous session at the head of the next session. Record the cutting itself in the ledger.
4. **Reconciliation against real code and real data**: for major findings, the adjudicating side reads back the real code and reconciles. For anomalies actually observed in production, run a separate track of investigation that identifies their structural cause.
5. **Dynamic verification (to the extent possible)**: for targets with an isolated environment, actually run abnormal inputs (corrupted state files, abnormal configuration values, combinations of missing pieces) and event sequences in changed orders, and observe the behavior. Mandatory dynamic trials in settleable form: when a disposition of an enumerated target of Step 1 can be settled in one of the following forms, do not close it with a static disposition alone; run a dynamic trial. (i) Evaluability: derive boundaries from the target's type (for datetime, the ends of the representable range and immediately before them; for numbers, the ends of the type and non-finite values; for strings, empty and maximum length). Do not treat having disposed of a datetime expression at a numeric type's boundary as a disposition. (ii) Environment premises of mandatory operations: by fault injection (making fsync, link, writes, and external calls fail), observe the remaining state and whether retry is possible. (iii) Acceptance of artifacts: actually run artifacts produced by the old version's producing side (including accumulated, multi-generation ones) through the new version's reader. Do not substitute reading the producing side's specification. (iv) Reachability and recovery paths: synthesize the necessary state, run normal processing over multiple cycles, and see whether the entry conditions are really met. A target that cannot be tried is left unverified, with the reason (do not mark it "confirmed" by a static disposition). The same standard applies when closing affirmatively: when closing an enumerated target as no-problem on the grounds of a protective mechanism's existence — "exceptions are caught", "the design is fail-closed", "a guard exists elsewhere" — actually inject the failure the protection is claimed to absorb, and close it only after observing not that no exception emerges, but the final state (whether the value, key, or output that should be obtained is actually obtained). When closing a reference (a read of a name, attribute, or key) as no-problem, include in the disposition an enumeration of the binding's assignment locations or confirmation of resolution by execution (confirming the shape of the referent, or confirming harmlessness on failure, is not a disposition). Place the oracle in mechanical signals (accounting conservation laws, consistency checks, attestation agreement, and the like), and record "findings estimated by reading" and "findings demonstrated by running" distinctly. For targets where dynamic verification cannot be performed, state that fact and the reason explicitly as not-performed. Reporting the effect: report the effect of dynamic verification not by coverage rate, execution count, or crash count, but by "the number and content of unique defects confirmed with reproduction procedures". When coverage figures are also given, annotate them as "reference values for the reached range; not evidence of defect discovery".
6. **Enumeration of invariants**: for each target, enumerate the relations that must not break (conservation of totals, idempotency, monotonicity, upper bounds) and make them audit viewpoints. Keep the enumerated invariants in the ledger as candidates for connection to change-time verification and runtime monitoring.
7. **Register an observed anomaly as a defect on the spot**: do not make attribution to an existing item or classification (regression / latent, whether covered by an existing item) a precondition for registering an anomalous behavior found in actual observation or in an audit. First register it, as the observed fact, in the ledger or the fix list, and perform classification and deduplication on registered items. "Covered by an existing item" may be said only after showing that the item's description includes the place and the shape of that failure. Placing coverage reconciliation at the entrance makes defects that do not fit a category fall before registration, in proportion to their misfit.

## Mode 1 (diff review)

- The population is the entire diff (all functional areas). The main focus is tracing "the chain of change × unchanged code" in Step 0; a changed line and the change in behavior of the unchanged code connected to it form one inspection unit.
- Judging regression vs. latent: for each finding, judge — by reconciliation against the real code — whether the same failure also holds on the baseline side (before the change). What does not hold on the baseline side is a regression; what does hold is latent (including what the change surfaced or amplified). Do not decide by impression.
- **Blocking classes**: in audits that include changes (diff reviews of a fix program and final checks), treat the following as blocking. (a) Conversion from adaptation to fixed values: a change that turns a computation which derived its reference from the environment or the counterparty (true UTC, the counterparty server's clock, the digits and units of specification data, etc.) into a form that holds only under a fixed environmental premise is sent back as a degradation at that point. A premise stated in a comment is not exculpatory. (b) New introduction of environment / counterparty premises: a new premise about time zones, server offsets, external naming schemes, locale / encoding, or OS conventions does not pass unless either the premise is removed, or it is declared and verified against a population defined from the recipient side. In distributed artifacts, define the verification population from the recipients (user environments × counterparty variation), not from the production environment; verification in the production environment alone is treated as unverified. Connected existing principle: "do not operate on fixed values; use a dynamic design in which numbers are derived from structure or determined by measurement".

## Mode 2 (full-codebase inspection)

- The population is the entire codebase (not a diff). Its purpose is auditing latent defects in existing code; do not narrow the range by whether changes exist.
- How to read: place as the main axis a longitudinal reading that traces the core behavior (what must always keep advancing in this system) from end to end, combined with sweeps by area. Place the enumeration of invariants (Step 6) at the center of the audit, and give dynamic verification with abnormal inputs (Step 5) a greater weight than in Mode 1.
- Classification: classify findings by severity and reachability (whether reachable in normal operation, or only under specific conditions, history, or environments). For findings whose reachability is condition-dependent, state the conditions in the finding.
- Ordering (conditional): only when the population exceeds the processing capacity of a single audit, you may allocate reading order and depth by features such as change size, spread, the novelty of an area, and past defect density. Ordering, however, is not a ground for exclusion (that the whole range is ultimately in scope is invariant); record the features used and the result of the allocation in the ledger. When the past data on which the allocation is based is old, state that explicitly.

## Reporting format

- In addition to a list of findings with severities, always include the following: (a) the discovery methods used and each method's coverage range; in a diff review, state explicitly whether the first pass was "behavior tracing" or a "class extraction sweep", and in the latter case do not call it a full-codebase inspection but an extraction check, and include the list of classes (b) **the methods not used, and the reasons** (a declaration of the coverage left out of scope) (c) the distinction between findings from static estimation and findings demonstrated dynamically (d) the unverified range, and what is needed to close it (e) the understanding scope of each range (fold Shallow into the unverified range) (f) a classification of findings by type (functional defect / evolvability defect), with tallies given per type (do not speak of coverage by the total count alone).
- Do not assert speculation as fact. Do not round an unverified range into "no problem".
- Keep the results in a ledger in the target workspace (code-audit-YYYYMMDD/ or the like). If there is a shortcoming attributable to your own way of proceeding, register it in the operations improvement record.
